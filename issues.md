# Technical audit of alleno-ora

The audited working tree fails to compile. After the build is restored, the highest-priority work is protecting workout data. Imports can leave partial records, file creation can overwrite existing content before validation, and pound values can be exported as kilograms.

## Scope and verification

The audit covered all four C++ source files, all three headers, CMake, the build script, the README, and relevant Git history. The source snapshot was based on commit `46ecd1b` with local edits. The critical build blocker comes from a local edit to `src/database.cpp`. The tracked version at `46ecd1b` contains the executable SQLite open call. Source line numbers refer to the audited working tree and can differ slightly from the committed versions.

A compiler syntax check across all four translation units reproduced the build error. SQL extracted from the source was exercised in an in-memory SQLite 3.37.2 database to verify constraints, ordering, and query plans. The CLI and existing build artifact were not run. Runtime examples below describe failure paths inferred from the source unless a check is named.

## Project and architecture

`alleno` is a C++20 command-line workout journal built by CMake as one executable with SQLite as its external library dependency. A working-directory-relative `config.txt` identifies the database and workout file locations. [Build configuration](CMakeLists.txt#L1) · [Config loading](src/main.cpp#L11)

| Component | Responsibility |
| --- | --- |
| [CLI](src/main.cpp#L86) | Loads configuration and dispatches template creation, import, date lookup, exercise history, and help. |
| [Workout model](include/workout.hpp#L13) | Represents workouts, exercises, and sets. The `Workout` class also parses files and prompts on the console. |
| [Database](include/database.hpp#L7) | Initializes the SQLite schema, writes workouts and their children, and retrieves workouts or working-set history. |
| [File](include/file.hpp#L8) | Writes templates and reports. It also owns validators that the workout parser and prompts call. |

The typical flow is to run `--create`, fill in the plain-text file, then run `--add` to store it in SQLite. `--get` reconstructs a workout by date, and `--exercise` writes working sets for one exercise across workouts. The small component count suits a local CLI. Separating parsing and validation from console and file I/O would let those behaviors be tested independently.

Before changing persisted data or enforcing a stricter format, settle whether more than one workout is allowed per date, whether to accept the legacy single rating alongside three current ratings, how to represent kg and lb for new and existing records, and under what conditions an output file may replace an existing file. ## Findings

Effort estimates are for one engineer and include focused regression checks. **Confirmed** indicates a defect established by source inspection or a named check. **Needs verification** identifies effects that depend on real data or a benchmark.

### Critical and high severity

| Severity and issue | Evidence and failure scenario | Recommended improvement | Effort and confidence |
| --- | --- | --- | --- |
| **Critical — Local working tree fails to compile** | The local edit comments out the `sqlite3_open` declaration. The compiler reported `SQLStatus` undeclared at both uses in `Database::open()`. [Database open](src/database.cpp#L16-L24) | Restore one executable open call and run a clean CMake build. | Under 1 hour. **Confirmed** |
| **High — Argument dispatch reads past the input** | The loop evaluates `args[i + 1]` before checking arity. Bare commands such as `--help` can hit this immediately. A successful import can reach it when the loop advances to the operand. Help also returns a failure code and configuration is loaded first. [Startup and dispatch](src/main.cpp#L86-L149) | Parse one command, validate arity, and dispatch once. Handle help first and return success. | ½–1 day. **Confirmed** |
| **High — Imports can persist partial or misassociated data** | The workout, exercise, and set inserts lack a shared transaction. The caller ignores set failures and can pass an SQLite error code as an exercise ID. If an exercise insert fails, the workout header can survive and make a retry look like a duplicate. [Import loop and exercise insert](src/database.cpp#L179-L229) | Use one connection and transaction for the whole import. Check every write, distinguish row IDs from failures, and roll back on failure. | 1–2 days. **Confirmed** |
| **High — SQLite handles and bound text have unsafe lifetimes** | Nested operations reopen into the same member pointer and lose the prior handle. Closing discards the result. The set insert binds a temporary string with `SQLITE_STATIC` and steps the statement after the string expires. Repeated child operations can leak handles, and SQLite may read invalid memory for the set type. [Connection ownership](src/database.cpp#L16-L30) · [Nested opens](src/database.cpp#L107-L146) · [Set binding](src/database.cpp#L249-L256) · [SQLite binding contract](https://www.sqlite.org/c3ref/bind_blob.html) · [SQLite close contract](https://www.sqlite.org/c3ref/close.html) | Give connections and prepared statements scoped ownership. Keep bound text alive for the required duration or have SQLite copy it. | 1–2 days, overlaps with transactions. **Confirmed** |
| **High — Creation and export can destroy existing files** | Template creation truncates the destination before collecting input and ignores input failure. Both exporters truncate directly and announce success without checking the completed write. Invalid input during `--create` can replace an existing workout with a partial header. [Template writer](src/file.cpp#L85-L99) · [Workout export](src/file.cpp#L101-L140) · [History export](src/file.cpp#L143-L172) | Validate first. Preserve existing files by default and publish output after a successful write. Return failures to the CLI. | 1–2 days. **Confirmed** |
| **High — Malformed inputs can be accepted or terminate the process** | Header matching uses substrings and fixed offsets, and the parser never checks required fields at EOF. Rating conversions can throw. Set extraction ignores failure and reuses state across lines and exercises. A blank file can parse successfully, a malformed rating can terminate the process, and a malformed set can retain a preceding value. [Headers and ratings](src/workout.cpp#L127-L212) · [Set parsing and EOF](src/workout.cpp#L227-L262) | Match exact field names and set grammar. Parse into fresh state, validate required fields and stream completion, and return line-numbered errors before writing to SQLite. | 2–3 days. **Confirmed** |
| **High — Pounds are silently relabeled as kilograms** | The documented format accepts pounds, but parsing discards the suffix, the schema stores just the number, and exports always append `kg`. An imported `135lbs` can be exported as `135kg`. [Documented units](README.md#L41-L47) · [Extraction](src/workout.cpp#L242-L251) · [Set schema](src/database.cpp#L82-L91) · [Export formatting](src/file.cpp#L125-L134) | Preserve explicit units or convert through an explicit unit model. Treat historical units as unknown unless another source establishes them. | 1–2 days after deciding unit policy. **Confirmed** |
| **High — Existing databases have no upgrade or recovery path** | Initialization skips any existing file and creates tables in separate statements. History before commit `41352cd` shows a schema with one `rating` column. Current inserts require newer columns, and reads decode positional `SELECT *` results without checking for NULL text. An old database can reject writes or fail on reads. An interrupted first initialization can leave a permanently incomplete schema. [Initialization](src/database.cpp#L37-L104) · [Insert columns](src/database.cpp#L149-L168) · [Row decoding](src/database.cpp#L270-L315) | Add versioned, transactional migrations. Select explicit columns, handle NULL values, and test migration of an old schema containing records. | 2–4 days. **Confirmed** incompatibility. Availability of real legacy data **needs verification**. |

### Medium and low severity

| Severity and issue | Evidence and failure scenario | Recommended improvement | Effort and confidence |
| --- | --- | --- | --- |
| **Medium — Operation failures can look like success or missing records** | The CLI ignores initialization and insert results. The duplicate check converts nonzero SQLite errors into `true`. Read loops stop on any non-row result and callers ignore child read failures. A query failure can be reported as a duplicate, or a child read failure can produce a partial export. [CLI result handling](src/main.cpp#L86-L149) · [Duplicate check](src/database.cpp#L107-L134) · [Nested reads](src/database.cpp#L310-L365) | Distinguish missing data, conflicts, and operational errors. Check SQLite statuses and return a nonzero exit code when a command fails. | 1–2 days, overlaps with persistence work. **Confirmed** |
| **Medium — Schema allows duplicate dates and orphan sets** | Date uniqueness is checked before inserting and is absent from the schema. Foreign keys are declared, but the app never enables enforcement. In-memory SQLite accepted a duplicate date and an orphan set using the local defaults. [Schema and foreign keys](src/database.cpp#L49-L91) · [Duplicate check before insert](src/database.cpp#L136-L149) | Enable foreign keys per connection, enforce the chosen workout identity, and report existing violations before applying constraints. | 1–2 days, overlaps with migrations. **Confirmed** |
| **Medium — Config and path handling depend on string layout** | Readers search for substrings and slice fixed offsets. A line containing only `db` can throw. Concatenation requires a trailing separator in the configured workout directory. Exercise names containing separators also affect generated output paths. [Config loading](src/main.cpp#L22-L68) · [Template path](src/main.cpp#L152-L162) · [History path](src/main.cpp#L194-L212) · [README config](README.md#L103-L113) | Parse exact keys once. Validate the database file and workout directory separately, join with filesystem paths, and enforce the chosen boundary for generated files. | 1–2 days. **Confirmed** |
| **Medium — Notes and dates can be misread** | Header checks take precedence over notes and blank lines are skipped. A note containing `Date` can trigger date validation. The date validator checks only the second separator and independent ranges, accepting impossible dates such as `2024/02/31`. [Header and notes parsing](src/workout.cpp#L133-L225) · [Date validator](src/file.cpp#L10-L25) | Treat notes as text until an exact closing marker. Validate full calendar dates and use a canonical date representation. | ½–1 day, overlaps with parser work. **Confirmed** |
| **Medium — History grouping depends on unspecified row order** | The query has no `ORDER BY`, and the reader and writer group adjacent dates. The exact query returned dates in order A, B, A against an interleaved fixture, which would produce two sections for date A. Detail queries also leave exercise and set order implicit. [Detail retrieval](src/database.cpp#L323-L375) · [History query and grouping](src/database.cpp#L418-L468) · [History writer](src/file.cpp#L150-L167) | Order by workout identity and stable within-workout keys. Verify grouping with an interleaved fixture. | ½ day. **Confirmed** |
| **Medium — No active automated verification** | The tracked tree has no active test suite, CTest registration, or CI workflow. The sole CMake target is the application. The model directly owns prompt and file parsing logic, making failure paths harder to exercise. [CMake targets](CMakeLists.txt#L13-L25) · [Console input](src/workout.cpp#L265-L342) | Add clean-build CI and CTest coverage for CLI exits, parser round trips, output preservation, transactional rollback, and migrations. Separate parsing from console I/O and use injected streams. | 2–4 days for the initial suite. **Confirmed** |
| **Medium — Documentation and executable disagree** | The documented `--save` flag is absent. The sample uses `Rating` and `Backoff sets`, which the current parser does not recognize. Importing the sample through `--add` can lose the rating and classify back-off sets as working sets. [README sample and flags](README.md#L7-L59) · [CLI options](src/main.cpp#L70-L95) · [Set headings](src/workout.cpp#L235-L251) | Decide what legacy input and flags to accept. Align help, README, template generation, parser, and exports, and turn the documented example into a regression fixture. | ½–1 day after deciding compatibility. **Confirmed** |
| **Low — Query and export costs grow unnecessarily** | In-memory query plans showed full scans for date lookup, exercises by workout, sets by exercise, and the sets input to history. Workout retrieval also issues a set query per exercise. History allocates an exercise per result row and copies results into a by-value writer parameter. [Detail reads](src/database.cpp#L323-L407) · [History assembly](src/database.cpp#L445-L473) · [Writer signature](src/file.cpp#L143) | Add indexes for lookup and join predicates with the migration. Use a smaller history representation and pass it by reference. Measure representative data before further changes. | 1–2 days. **Confirmed** scans and copies. User impact **needs verification**. |
| **Low — Build and dependency assumptions are implicit** | The script assumes its working directory and Make, and it proceeds to `make` after a configure failure. CMake discovers system SQLite without declaring a tested version range. The local SQLite version observed was 3.37.2. Vendor patch status was outside the audit. [Build script](build/build.sh#L1-L2) · [Build configuration](CMakeLists.txt#L1-L8) | Document a generator-independent CMake command and verify it in CI. ## Security and privacy scope

Queries bind user-controlled SQL values as parameters. No credentials surfaced in the current application source or documented configuration. The main security concerns in scope are unsafe file writes, C++ object lifetimes, and local data integrity. The current checkout has no database. The historical `database/workouts.db` blob was zero bytes, and an old config contained absolute local paths. The audit did not assess package advisories or exhaustively scan Git history for secrets. ## Overall assessment and prioritized action plan

The project has a clear purpose and a codebase small enough to repair incrementally. The immediate blocker is compilation in the audited working tree. The main operational risk once it compiles is silent loss or alteration of normal workout data.

1. **Immediate correctness and security.** Restore the open call first. Validate CLI operands before dispatch, prevent premature file truncation, and return failures to callers. These are small changes that stop destructive behavior and make regression failures visible.
2. **Immediate correctness and security.** Fix connection and statement ownership, make imports atomic, and add schema versioning. Resolve workout identity, rating compatibility, and units before applying constraints. Verify rollback, legacy migration, and mixed-unit round trips.
3. **High-value maintainability and architecture.** Keep the single executable and SQLite backend. Separate parsing and serialization from prompting, file ownership, and exit codes. Add CTest and clean-build CI, make export order deterministic, and align the README with tested behavior.
4. **Optional refinements and modernization.** Measure representative histories, add indexes for observed access patterns, simplify history result handling where it reduces allocations and copies, and verify the supported build configurations.
